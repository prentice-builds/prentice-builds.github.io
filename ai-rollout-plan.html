AI rollout plan

The first eighteen months of bringing AI into a project delivery team. The report says the path is deliberate. Automate the repeatable work, build targeted reviews next, and connect them over time. This is that path on a calendar.

It starts where most teams already are. The firm has AI tools and people are using them, and often no one is clearly accountable for working out what they are for. Every stage ends with a test, and a team moves on when it passes, not when the date arrives.

The stages overlap on purpose. One tool is in pilot while the next is being built. The dates assume the firm has a tool that can do the work, or approves one in time. A slow security or legal review moves everything after it.

Two things run the whole way

Bringing people along. Some project managers will be excited. Some will worry that this is how their job goes away. Some will not want to change how they work, and some will wait to see whether it lasts. All of those reactions are reasonable, and the plan has to make room for them.

That means saying plainly what the work is for, starting with the people who want to try it, and never requiring a tool before it has passed its test. It means adding one or two changes at a time, and holding a regular update where the team hears what is being built and can say what is not working. A rollout that moves faster than the team can absorb will be resisted, however good the tools are.

Getting better as you go. Nothing here is finished when it launches. Each tool is scored again after it spreads, the corrections people make are kept and folded back in, and tools nobody uses are retired. The rollout itself gets the same treatment. On a regular schedule the team looks at what is working, what to stop, and what the roadmap should say next.

Every tool goes through the same cycle

  1. DesignWrite the SOP with the people who do the task
  2. BuildBuild or configure the tool against it
  3. TestRun it on examples with known answers
  4. PilotA small team, scored against a bar
  5. Roll outTo the rest of the team, one tool at a time
  6. ImproveFix what people report, retire what is not used

Several of these run at once. They converge in the last stage, when the tools that have earned trust are connected to each other.

The first ninety days

Days 1 to 30

Establish the starting point

  • Name one person accountable for the work.
  • Tell the team what this is before anything gets measured. The log measures the work, not the person.
  • Have every project manager log a typical week and a week when monthly reports are due.
  • List the AI tools already approved and what each one can do.
  • Learn how a new tool gets approved, who signs off, and how long it takes.
  • Read the client agreements. List which projects can use AI tools and which cannot.

Done whenThere is a baseline from both weeks, a list of approved tools, a clear approval process, and a named person.

Use the weekly baseline, the client data answer in fair questions, and the description of the AI role

Days 31 to 60

Choose the first tasks and design for them

  • Turn this plan into a roadmap for your own program or client account, and get the client and the team's leaders to sign off on it.
  • Pick the first one or two tasks from the baseline. Choose for speed, a repeatable task an approved tool can handle.
  • Write the SOP for each task with the project managers who do it. How the work is really done is the design brief for the tool.
  • Set the bar each tool will be held to.
  • Start a short, regular update for the whole team. Say what is being built and what is not changing.

Done whenThe roadmap is signed off, the first tasks are chosen, and each one has an SOP and a bar.

Use the start here view in the opportunity landscape and the pilot scorecard

Days 61 to 90

Build the first tool and test it

  • Build or configure the tool against the SOP.
  • Test it on real examples with known answers, alongside two or three project managers.
  • Fix what the test shows, and feed what you learn back into the SOP.
  • Choose the pilot group, starting with people who want to try it.

Done whenOne tool has passed its test and a small team is ready to pilot it.

The next fifteen months

Day 90 to month 6

Roll out the first tool and start the first review

  • Run the pilot with the small team and score it against the bar.
  • Improve the tool from what they report, then roll it out to the rest of the team with its SOP and someone to ask.
  • Start the first review alongside it, a change order or a pay application, if the firm has a tool that can do it. Write the rules with the project managers who do the review, build it, and test it on documents with known answers.
  • If no approved tool can do the review, use the pilot's results to make the case for one and start its approval.

Done whenThe first tool is in daily use across the team, and the first review is built and tested or its tool is in approval.

Use the pilot scorecard and see a first review in the review prototypes

Month 6 to 12

Repeat the cycle

  • Pilot the first review, hold it to a bar for being right before it gets credit for saving time, then roll it out.
  • Keep going. Build and test three to five tools in the first year, each through the same cycle.
  • Build ahead of the team if you can, and release one tool at a time. A team can only absorb so much change at once.
  • Run the baseline again, both weeks, and see what has moved.
  • Ask the people using each tool what to fix. Retire what is not used.

Done whenThree to five tools have passed their tests, the ones released are in daily use, and a second baseline shows where the hours went.

Month 12 to 18

Take it wider, move to agents, and start connecting

  • Roll out what has passed to the wider organization, with the SOPs, the test results, and the lessons from the first team.
  • Turn the trusted reviews into agents. An agent watches for the document, reads the contract and project records it needs, drafts the review with its sources, and hands it to the project manager to confirm or correct.
  • Keep those corrections, so each review is better than the last.
  • Start the synthesis layer by linking two agents. A submittal waiting on approval is routine. On equipment with a long lead time it is a schedule risk, and only a tool reading both records sees it.
  • Make each finding arrive with its evidence, whose court it is in, and a date to act by.
  • Keep building new tools, and connect each one once the team relies on it.
  • Revise the roadmap with the team. By now the project managers should be proposing what to build next.

Done whenThe tools are in use beyond the first team, the first reviews run as agents, and the team has acted on one finding that no single review would have caught.

What holds at every stage

The project manager makes every decision. Nothing is approved by a tool, in month one or month eighteen.

Each step proves its value before the next one is funded. A stage that has not passed its test is not finished, whatever the calendar says.

The tools are built with the people who will use them. That is how trust forms, and trust is what gets a tool used.

What this is and is not

It is a rough sequence. The real roadmap is the one a team writes for its own program in the first sixty days.

A firm with no AI tools at all needs a business case for them first, and a longer plan. And three to five tools in a year is a pace that depends on what can be bought and on the help the accountable person has.

Tool approval is the part most likely to stretch it. A slower security review or stricter client agreements can push the first reviews well past month 6. The dates can move. The order should not.
